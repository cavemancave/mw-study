# 第 6 章：高性能通信与性能工程

## 本章目标

能围绕延迟、吞吐、抖动、CPU、内存、带宽和磁盘 I/O 建立基线，定位瓶颈，并用可重复实验验证优化。

## 6.1 先定义指标

- 端到端延迟：产生到消费完成。
- 分段延迟：排队、编码、传输、解码、调度和处理。
- 吞吐：消息/秒和字节/秒。
- 抖动：p95、p99、最大值和 deadline miss。
- 资源：CPU、RSS、分配次数、内存带宽、网络带宽、IOPS。
- 稳定性：丢帧、重传、超时、重连和恢复时间。

均值不能代表尾延迟。测试报告必须固定消息大小、频率、订阅者数量、CPU 亲和性、网络、数据集和构建配置。

## 6.2 拷贝、批量和内存布局

减少拷贝的手段包括 move、buffer pool、预分配、批量消息、共享内存和 loaned message。代价是生命周期和回收复杂度增加。改善缓存局部性，避免不必要的指针跳转和 false sharing；结构体布局要考虑对齐和热冷字段分离。

## 6.3 背压和资源隔离

每条数据流都要有容量预算。满队列策略可以是阻塞、丢新、丢旧、采样或按优先级丢弃。大图像处理、写盘和云上传应使用独立资源池，不能让慢消费者占满控制路径的线程和内存。

## 6.4 Linux 工具链

- `perf` 和火焰图：CPU 热点、锁和调度。
- `pidstat`、`iostat`、`ss`：进程、磁盘和网络。
- `strace`：系统调用和阻塞点。
- ASan/UBSan/TSan：内存和并发缺陷。
- eBPF、LTTng、trace-cmd：系统级时序和跨进程追踪。

优化步骤应是：假设 -> 基线 -> 定位 -> 单变量修改 -> 重测 -> 检查副作用。

## 6.5 真实案例：平均 4 ms，p99 180 ms

分段 trace 发现大多数消息很快，但写盘偶发阻塞导致队列等待，尾延迟暴涨。修复重点不是继续优化序列化，而是隔离写盘、批量 I/O、限制队列和对高频流采用丢旧策略。

## 6.6 实验与验收

实现一个发布者和多个订阅者，分别测试复制、共享 buffer、不同队列深度、不同消息大小和慢消费者。记录 p50/p95/p99、吞吐、CPU、RSS、带宽和丢帧，输出一份基线与优化报告。

验收标准：每个优化结论都有测试条件和数据；能指出吞吐增加是否牺牲了尾延迟或内存；能解释为何一个方案适用于图像但不适用于控制。

## 面试问题与参考答案

**问：如何优化一条高频链路？**

答：先建立分段和端到端基线，确认瓶颈在拷贝、编码、锁、排队、网络还是磁盘；再按收益优化，并同时观察 p99、CPU、内存、带宽和丢帧。没有测量就不能声称优化有效。

**问：零拷贝的主要风险是什么？**

答：buffer 生命周期、并发读写、跨进程崩溃回收、权限、对齐和版本兼容。它减少了某类成本，不会自动解决调度、排队和网络瓶颈。

**问：如何估算带宽？**

答：先算原始数据率：消息大小乘频率乘路数，再加入协议头、重传、压缩变化和峰值突发。分别计算平均和峰值，并保留拥塞和故障恢复余量。
