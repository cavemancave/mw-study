# 第 1 章：中间件全景与通信抽象

## 本章目标

你需要从“写一个网络程序”切换到“设计一套通信语义”：知道谁和谁通信、数据是什么性质、失败如何表达，以及中间件和业务节点的边界在哪里。

## 1.1 机器人系统的基本组成

机器人通常由驱动、感知、定位、融合、规划、控制、日志和云端协同等模块组成。模块可以是同一进程中的组件，也可以是不同进程、不同主机甚至不同网络域中的节点。

- **Node**：拥有身份、生命周期、输入输出和健康状态的计算单元。
- **Topic**：持续的数据流，适合传感器、状态和事件。
- **Service**：有明确请求和响应的短操作。
- **Action**：可取消、有反馈、最终有结果的长操作。
- **Data plane**：图像、点云、IMU 等大量业务数据。
- **Control plane**：发现、配置、健康、拓扑、租约和路由策略。

发布者不应依赖消费者的具体实现；消费者也不应假设发布者永远在线。中间件的价值正是把这种不确定性变成明确协议。

## 1.2 一条消息经过什么

```text
业务产生 -> 队列 -> 编码 -> 路由/发现 -> 传输 -> 接收缓存
    -> 解码 -> 调度回调 -> 业务处理 -> 观测与确认
```

每一步都可能增加延迟、拷贝、分配或失败。设计时应明确消息 ID、来源、序列号、时间戳、schema 版本和 deadline。

## 1.3 通信语义的选择

| 需求 | 推荐语义 | 主要问题 |
| --- | --- | --- |
| 高频传感器 | Pub-Sub | 旧数据是否应丢弃 |
| 参数查询 | Service | 超时和服务不可用 |
| 导航任务 | Action | 取消、反馈和幂等 |
| 全局配置 | 可靠事件/快照 | 版本和一致性 |
| 大文件上传 | 分片流 | 断点续传和校验 |

不要用 Service 模拟持续流，也不要用无限重试的 Topic 传递必须只执行一次的控制命令。

## 1.4 真实案例：相机到控制器

一帧 1920x1080 的 RGB 图像约为 6 MB，30 FPS 时原始数据约 180 MB/s。相机链路关注吞吐、内存带宽和丢帧；控制指令关注 deadline、顺序、过期检测和安全降级。两者不能简单共用同一个无限可靠队列。

## 1.5 实验与验收

画出一个包含相机、IMU、检测、规划和控制器的计算图，并给每条边标注：频率、大小、时效性、可靠性、队列深度和丢弃策略。然后为每条消息设计一个头部：`message_id`、`source_id`、`sequence`、`source_timestamp`、`schema_version` 和 `deadline`。

验收标准：你能解释每个字段如何用于去重、排序、延迟测量或版本兼容，并能说明慢消费者会影响哪条链路。

## 面试问题与参考答案

**问：中间件和业务算法如何分层？**

答：中间件负责发现、传输、序列化、调度、QoS、容错和观测；算法节点负责业务语义。中间件应通过稳定的数据契约提供能力，不感知检测或规划的内部逻辑。

**问：为什么需要数据平面和控制平面？**

答：大数据流追求吞吐和低拷贝，发现、健康和配置追求可达性和一致性。分离后可以给控制消息更高优先级，避免图像拥塞阻塞重连和安全控制。

**问：Topic、Service、Action 如何区分？**

答：Topic 是异步持续流，Service 是短请求响应，Action 是带反馈和取消的长任务。区别本质是生命周期、时效性、错误和重试语义不同。
