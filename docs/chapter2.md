# 第 2 章：现代 C++ 与 Linux 基础设施

## 本章目标

把已有的 C++ 和 Linux 经验用于长期运行的基础设施：明确所有权，设计可停止的线程，选择进程间通信方式，并理解内存和事件循环对延迟的影响。

## 2.1 生命周期和取消

中间件有三类生命周期：节点生命周期、连接生命周期和消息生命周期。每类都要有创建、就绪、失败、停止和销毁状态。

推荐使用 RAII 管理 fd、共享内存映射、线程和订阅句柄；使用 `std::jthread`/`stop_token` 或明确的停止标志管理线程；用条件变量、`eventfd`、关闭 fd 或超时等待唤醒阻塞操作。不要强杀线程，也不要让析构函数永远等待。

## 2.2 线程模型

常见角色包括接收线程、序列化线程、路由线程、回调线程、写盘线程和监控线程。不要默认“一条消息一个线程”。更可控的设计是固定线程池、按优先级分组、每路有界队列和明确的所有权。

关注：锁竞争、优先级反转、false sharing、回调重入、线程栈、CPU 亲和性和 NUMA。无锁队列只有在基线证明锁是瓶颈，并且内存回收协议清楚时才值得使用。

## 2.3 IPC 选择

- 同进程：直接调用或环形队列，延迟最低但隔离弱。
- Unix domain socket：适合控制面和小消息，支持 fd 传递。
- `mmap`/共享内存：适合大 buffer，必须设计生命周期、权限和崩溃恢复。
- `eventfd`/`timerfd`：适合将通知和定时器纳入 `epoll`。
- TCP/UDP：适合跨主机，应用层仍需定义消息边界和失败语义。

## 2.4 事件循环和消息边界

TCP 是字节流，必须使用长度前缀、固定头部或自描述帧处理部分读写。发送同样可能部分写。事件循环中不要执行慢序列化、磁盘写入或阻塞锁等待，否则所有连接共享的线程都会被拖住。

## 2.5 真实案例：慢磁盘拖垮接收线程

录制进程用一个全局锁保护所有 topic 队列，写盘线程执行 `fsync` 时持锁，网络接收线程无法入队，最终所有传感器同时丢帧。修复方式是采集和写盘解耦：接收线程只做轻量封装并入有界队列，写盘线程批量写入，队列满时按消息语义丢旧或降级。

## 2.6 实验与验收

实现一个 C++ 多生产者、多消费者有界队列，并增加：优雅停止、超时入队/出队、队列水位、丢弃计数和 TSan 测试。再用 Unix socket 实现控制面，用共享内存传输一个大 buffer。

验收标准：能处理生产者退出、消费者变慢、主进程收到 SIGTERM、共享内存 owner 崩溃，并且没有线程泄漏、数据竞争或无限增长。

## 面试问题与参考答案

**问：如何安全停止阻塞线程？**

答：通过停止协议唤醒阻塞点：条件变量配合谓词、`eventfd`、超时或关闭 fd；线程看到停止请求后释放资源并退出，主线程最后 `join`。还要验证回调不会访问已析构对象。

**问：共享内存为什么不等于零拷贝？**

答：数据可能仍需从业务对象复制到共享区，接收方也可能反序列化复制。真正零拷贝还要解决 buffer 所有权、引用计数、对齐、跨进程崩溃回收和版本兼容。

**问：什么时候不用无锁队列？**

答：当锁不是已证实瓶颈，或无法明确满队列、内存回收和生命周期语义时。有界锁队列更易验证和观测，通常应先建立它的性能基线。
