# 第 4 章：发布订阅、QoS、发现与路由

## 本章目标

掌握中间件最核心的控制逻辑：发布者和订阅者如何匹配，消息如何进入队列，QoS 如何决定行为，节点如何发现彼此，以及慢消费者和跨域路由如何处理。

## 4.1 发布订阅内部结构

一个最小总线包含 topic registry、publisher registry、subscription registry、匹配器、每订阅者队列、发送器和统计模块。发布流程通常是：校验类型和权限 -> 找到匹配订阅者 -> 根据 QoS 入队或丢弃 -> 异步发送/回调 -> 更新指标。

发布者不应被任意一个慢订阅者同步阻塞。每个订阅者需要独立的队列和水位；队列满时按 topic 语义选择阻塞、丢旧、丢新、采样或降级。

## 4.2 QoS 是行为契约

QoS 至少包括可靠性、history、队列深度、deadline、寿命、持久性、顺序、优先级和资源上限。`reliable` 不是“永不丢失”，它通常意味着传输层确认和重传，但仍受 deadline、队列、进程崩溃和磁盘能力限制。

- IMU：高频，常需 latest-value、有限深度和低延迟。
- 控制命令：可靠、带 deadline、序列号和过期检查。
- 检测结果：可有限重试，但不能无限堆积旧结果。
- 诊断日志：低优先级、批量和可延迟。

## 4.3 服务发现

发现信息应包括 node ID、topic/service、类型、版本、端点、QoS、能力、健康状态和租约。心跳或 lease 过期后应撤销匹配。固定 IP 只能解决静态寻址，不能表达动态启动、迁移、重启和能力变化。

发现协议要考虑：重复公告、过期消息、身份冲突、网络分区、启动风暴和安全认证。小规模单机可用本地 registry；多机系统需要 gossip、中心 registry 或 DDS/Zenoh 等框架机制。

## 4.4 路由和网关

直连延迟低但跨网域管理困难；代理路由便于策略、鉴权和缓存，但会增加跳数和瓶颈。云边端场景通常让控制面经过网关，大数据流尽量边缘直连或使用专门数据通道。路由表要有版本和 TTL，避免旧拓扑长期生效。

## 4.5 真实案例：IMU 被可靠队列拖出延迟

IMU 200 Hz，控制器只需要最新样本。如果使用深度很大的可靠队列，消费者短暂停顿后会处理一串已经过期的样本，控制延迟上升。更合理的是限制深度、检测 deadline、丢弃旧数据，并把“最新状态”与“必须逐条处理的事件”区分开。

## 4.6 实验与验收

实现一个进程内 topic bus：支持 topic/type 匹配、每订阅者有界队列、best effort/reliable 两种模式、deadline 和慢消费者统计。加入发现租约，模拟发布者重启和订阅者变慢。

验收标准：一个慢订阅者不能阻塞其他订阅者；QoS 不匹配有明确诊断；租约过期后不再投递；指标能显示队列水位、丢弃、重传和延迟。

## 面试问题与参考答案

**问：QoS 不匹配时怎么办？**

答：启动或匹配阶段应检查兼容矩阵并输出原因，例如 reliability、history 或类型不兼容；不能让业务只看到“偶尔收不到消息”。

**问：背压还是丢消息？**

答：按语义选择。任务结果、配置和安全事件通常需要可靠处理；高频传感器和视频通常丢旧保新；无限队列不是背压方案，只会把拥塞变成内存和延迟问题。

**问：重试会不会破坏消息顺序？**

答：会，尤其是并行重试或重连后旧连接消息到达。需要序列号、连接代际、幂等处理和过期检查，必要时为每个流串行化确认。
