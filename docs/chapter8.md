# 第 8 章：录制、存储、索引与回放

## 本章目标

设计从采集到离线分析的数据闭环：高频数据不阻塞业务，文件可检索、可校验、可恢复，回放可以重现线上问题。

## 8.1 数据链路

```text
订阅 -> 轻量封装 -> 有界缓存 -> chunk 聚合 -> 压缩 -> 顺序写入
                                  -> 索引 -> 上传/回放
```

采集线程不能等待磁盘；写盘线程要批量 I/O。缓存必须有容量和水位，满时根据数据等级执行丢弃、降采样或暂停低优先级流。

## 8.2 格式、chunk 和索引

可使用 MCAP 或 ROS bag 作为工程格式，也可以设计自有容器。一个合理容器包含文件头、schema/channel 定义、数据 chunk、索引和尾部提交信息。索引至少支持按 topic/channel 和时间范围检索；chunk 边界要兼顾压缩收益、随机访问和损坏隔离。

记录源时间、接收时间、单调时间、序列号、设备 ID、schema 版本和校验和。已压缩的 JPEG/H.264 通常不值得再次压缩；点云、文本和结构化元数据可分别选择压缩策略。

## 8.3 异常恢复

顺序写入可能在进程崩溃或断电时留下半个 chunk。启动恢复时扫描长度、magic、版本、CRC 和提交标记，保留完整 chunk，截断或标记不完整尾部，并重建索引。上传要支持分片、校验、断点续传和幂等。

## 8.4 回放语义

回放应支持原速、倍速、时间段过滤、topic 过滤、暂停、单步和仿真时钟。确定性测试需要控制时间推进和输入顺序；如果回放直接依赖墙上时间，线上 bug 可能无法稳定复现。

## 8.5 真实案例：索引未完成导致整段数据不可用

录制进程在索引写入前崩溃。如果读取器只认完整尾部索引，所有已写数据都会不可见。更健壮的方案是读取完整 chunk，校验后重建索引；索引是加速结构，不应成为唯一事实来源。

## 8.6 实验与验收

实现一个按 channel 写入 chunk 的录制器，加入 CRC、临时文件/提交标志、时间索引和压缩。随机在写入、索引和上传阶段杀死进程，重启后执行恢复，再回放并核对消息 ID 和 payload。

验收标准：恢复不会返回损坏消息；索引可重建；回放支持过滤和倍速；报告写入带宽、队列水位、丢弃数、压缩率和恢复时间。

## 面试问题与参考答案

**问：如何设计高吞吐录制器？**

答：采集线程只做轻量封装并入有界队列；专门线程批量聚合和顺序写入；索引异步构建；不同数据流隔离并按优先级降级；用队列水位、写入带宽、fsync 时间和丢弃数验证。

**问：为什么索引不能是唯一事实？**

答：索引更新可能晚于数据写入，也可能在崩溃时丢失。完整数据 chunk 和校验才是事实，索引应可扫描重建。

**问：回放和线上运行为什么要使用同一接口？**

答：这样可以让算法节点不知道数据来自实时设备还是文件，减少测试分支，并支持线上问题离线重现。时间源和 QoS 仍需显式配置。
