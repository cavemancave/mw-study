# 第 9 章：Multi-Agent 与分布式状态

## 本章目标

掌握多机器人协同通信中的身份、能力、状态同步、任务租约、弱网容错和最终收敛，不把单机 topic 总线简单复制到多智能体系统。

## 9.1 身份和能力发现

每个 agent 需要稳定 ID、启动 epoch、设备/软件版本、能力列表、位置和健康状态。能力描述应可版本化，例如“搬运能力”还要包含载荷、区域、当前占用和有效期。发现信息需要 TTL，不能相信永久在线。

## 9.2 状态同步

实时状态通常采用“带版本的增量 + 周期性全量快照”。接收方检测到版本缺口时请求快照；重复增量幂等处理；旧版本不能覆盖新版本。对集合状态可使用 owner、版本、删除标记或 CRDT 风格的合并规则。

## 9.3 任务协同和租约

任务消息至少包含 task ID、owner、epoch、状态、deadline 和幂等键。调度器分配带租约的任务；agent 执行前校验租约和 epoch；续租失败后停止或进入安全状态。任务结果重复到达不能造成重复副作用。

## 9.4 弱网和网络分区

需要处理丢包、重复、乱序、延迟、断线、带宽变化和时钟漂移。不要无限重试；按消息语义设计：控制命令有 deadline 和幂等，状态通过快照收敛，日志本地缓存后补传，安全事件持久化确认。

## 9.5 真实案例：失联机器人重连造成双主

机器人 A 失联，调度器将任务转移给 B；A 延迟重连并继续执行旧任务。如果任务没有 epoch/租约校验，就会出现双主。新 owner 获得更高 epoch，所有带旧 epoch 的执行和结果都被拒绝或转为只读上报。

## 9.6 实验与验收

模拟 5 到 20 个 agent，实现心跳、能力注册、状态快照/增量、任务租约和断线重连。注入分区、延迟、乱序、重复和带宽限制，观察状态是否收敛以及任务是否出现双主。

验收标准：重连后能补齐状态；旧消息不会覆盖新状态；任务执行幂等；网络恢复后拓扑和能力最终一致；所有超时和拒绝都有原因码。

## 面试问题与参考答案

**问：状态同步为什么要全量和增量结合？**

答：增量节省带宽，全量提供恢复和基线。正常运行收增量，检测到缺口或周期到达时取快照，再继续按版本接收增量。

**问：为什么不能只依赖本地时间戳？**

答：时钟可能漂移、跳变或未同步，本地时间不能可靠表达因果。顺序应使用序列号、epoch 或逻辑版本，延迟测量使用单调时钟。

**问：弱网下可靠性的正确目标是什么？**

答：不是无限重试，而是让每类消息在截止时间和业务风险内达到可接受语义：状态可收敛、命令不重复副作用、日志可补传、安全事件可确认。
