# 第 3 章：消息模型与数据契约

## 本章目标

学会设计可跨进程、跨主机、跨语言和跨版本使用的消息，而不是只把 C++ 对象的内存布局直接发出去。

## 3.1 消息头部

建议把传输元数据和业务 payload 分开。头部至少考虑：类型或 topic、schema ID、版本、消息 ID、来源、序列号、源时间、发送时间、deadline、payload 长度和校验信息。

- 源时间用于传感器对齐。
- 单调时间用于本机延迟测量。
- 序列号用于检测缺口和乱序。
- schema ID 用于选择解码器。
- deadline 用于丢弃已无价值的消息。

## 3.2 序列化选型

| 方案 | 优点 | 代价与适用边界 |
| --- | --- | --- |
| Protobuf | 跨语言、生态成熟、演进规则清晰 | 解析和分配成本较高 |
| FlatBuffers | 可直接访问 buffer，适合低延迟 | schema 约束和使用复杂度更高 |
| IDL | 可生成类型和接口，适合框架契约 | 依赖工具链和代码生成规范 |
| 固定布局 | 解析快、可预测 | 演进和跨语言更困难 |

选择要用基准数据验证：编码耗时、解码耗时、消息大小、分配次数、峰值内存和端到端 p99。

## 3.3 版本兼容

Protobuf 等 schema 演进应遵守：字段编号不复用；删除字段保留编号；新增字段给出合理默认值；旧消费者忽略未知字段；语义变化通过新版本或转换层表达。字段类型相同不代表语义兼容，坐标系、单位、时间基准和置信度含义也必须版本化或显式描述。

## 3.4 大对象和生命周期

图像、点云不应在每个阶段都完整复制。可以用 buffer pool、引用计数句柄、共享内存 loan 或分块 payload。句柄必须带长度、容量、owner 和回收状态；不能把指向临时 vector 的裸指针放入异步队列。

## 3.5 真实案例：米和毫米的静默错误

将坐标字段从米改为毫米，如果只改变注释，旧消费者会得到数量级错误却不一定崩溃。应固定单位，或增加 schema 版本和转换层；回放工具遇到未知版本应明确报错，不能静默按旧格式解释。

## 3.6 实验与验收

使用 Protobuf 或 FlatBuffers 定义 IMU、图像元数据和控制命令。写一个新旧版本互读测试，覆盖新增字段、删除字段、未知字段和单位变化；再测量对象序列化与 buffer 直接访问的性能。

验收标准：旧消费者能读取兼容的新消息；不兼容变化能被检测；测试报告包括消息大小、CPU、分配和 p99。

## 面试问题与参考答案

**问：Protobuf 为什么不一定适合点云？**

答：点云大且频率高，逐字段解析和对象分配可能消耗大量 CPU 和内存带宽。可以考虑 FlatBuffers、固定布局或专用块格式，但必须用端到端测试证明收益。

**问：如何设计跨语言数据契约？**

答：用 IDL/schema 作为唯一来源，生成各语言类型，固定字段编号和单位，消息携带版本和 schema ID；在 CI 中运行兼容性测试，不依赖某种语言的内存布局。

**问：消息 ID 和序列号有什么区别？**

答：消息 ID 通常用于全局去重和追踪，序列号用于同一来源同一流的顺序、缺口和最新值判断。二者可以同时存在，不能用一个字段承担所有语义。
