# 第 10 章：可靠性与可观测性

## 本章目标

让通信链路可以失败、恢复和解释。你需要设计状态机、超时重试、限流降级、健康检查、trace 和故障注入，而不是只在成功路径上验证收发。

## 10.1 超时和重试

所有等待都应有 deadline。重试使用指数退避和随机抖动，并设置最大次数、总预算和错误分类。连接代际要防止旧连接消息污染新状态；操作要有幂等键或去重表。

重试风暴通常来自多个节点同时超时后立即重试。控制、心跳、数据和上传应有独立优先级、连接或带宽配额。

## 10.2 状态机

至少为连接、订阅、发现、录制和上传建模：`Disconnected -> Connecting -> Ready -> Degraded -> Backoff`。每次状态迁移记录原因、时间、代际和待处理动作。状态机比散落的布尔变量更容易测试和诊断。

## 10.3 限流和降级

根据队列水位、CPU、内存、磁盘和带宽做动态决策：降低日志等级、减少图像帧率、丢弃低优先级数据、停止非关键上传，但不能让控制闭环依赖云端。降级策略必须可见、可恢复且有安全边界。

## 10.4 Trace 和指标

为消息设置 message ID 和 trace ID，在采集、入队、编码、发送、接收、解码、回调、写盘和上传处记录 span。核心指标包括 p50/p95/p99、队列水位、丢弃、重传、deadline miss、连接状态、磁盘错误、恢复时间和数据校验失败。

日志应结构化，包含 node、topic、peer、message、error code 和状态变化，避免只输出无法关联的自然语言。

## 10.5 真实案例：云端不可用

机器人控制和安全停车必须留在边缘。云端不可用时，本地继续运行，关键数据缓存，上传以低优先级补传；重试不能挤占控制通道。监控中应能区分云端故障、边缘缓存堆积和本地磁盘不足。

## 10.6 故障注入实验

注入丢包、乱序、重复、延迟、断网、进程杀死、磁盘满、索引损坏、时钟跳变和慢消费者。验证消息语义、状态收敛、重复执行、恢复时间、告警和 trace 是否完整。

## 面试问题与参考答案

**问：重试为什么会放大故障？**

答：同步重试会在拥塞时形成重试风暴，消耗更多 CPU 和带宽。需要退避、抖动、总预算、错误分类和优先级隔离。

**问：怎样判断系统真的可靠？**

答：定义故障模型和可接受语义，再通过故障注入验证：消息是否重复执行、状态是否收敛、数据是否可恢复、恢复时间是否达标、指标是否能定位原因。只跑成功路径不能证明可靠。

**问：日志和 trace 的区别？**

答：日志适合记录离散事件和上下文，trace 描述一个请求或消息跨线程、进程和机器的时序；二者通过 trace ID、message ID 和时间关联。
