# 第 11 章：综合项目与面试

## 本章目标

把前十章变成可以展示、压测和讲清楚的工程项目，并建立系统设计题的答题框架。

## 11.1 项目分阶段实现

### 阶段一：单机通信骨架

实现 C++ topic bus：Unix socket 控制面、共享内存或 mmap 数据面、topic/type 匹配、序列号、有界队列和优雅停止。

### 阶段二：框架接入

用 ROS 2 实现 IMU、图像、控制 topic，加入 service/action，比较 QoS、executor、RMW 和进程边界。

### 阶段三：录制回放

用 MCAP 或 ROS bag 记录数据，支持 chunk、索引、压缩、CRC、恢复、时间过滤和倍速回放。

### 阶段四：多智能体

模拟 5 到 20 个机器人，实现发现、心跳、能力、状态快照/增量、任务租约、epoch 和弱网注入。

### 阶段五：性能和可靠性报告

输出基线、优化前后数据、故障注入结果和设计取舍，不只展示代码。

## 11.2 验收指标

至少报告：

- 端到端 p50/p95/p99 和最大延迟。
- 消息/秒、字节/秒和峰值突发。
- CPU、RSS、内存分配、网络带宽和磁盘写入。
- 丢帧、重传、deadline miss、断线重连和恢复时间。
- 录制压缩率、索引查询耗时和损坏恢复结果。
- 多 agent 状态收敛时间、任务重复率和网络分区行为。

报告必须写清硬件、内核、编译选项、消息大小、频率、消费者数量和网络条件。

## 11.3 系统设计答题模板

1. 明确数据类型、频率、大小、时效性和可靠性目标。
2. 区分控制平面、数据平面和存储平面。
3. 画出节点、进程、机器、网络域和消息路径。
4. 选择传输、序列化、发现、QoS、队列和路由并解释取舍。
5. 说明慢消费者、重复、乱序、断网、重启、磁盘满和版本升级。
6. 给出容量估算、指标、压测和故障注入方案。
7. 说明安全、兼容、部署、灰度和回滚。

## 11.4 高频面试问题

**问：为什么不用自研 TCP 代替 ROS 2/DDS？**

答：自研可以针对特定链路优化，但还要自行解决类型、发现、QoS、生命周期、工具、诊断和兼容。若系统需要完整机器人生态，优先利用成熟框架；在明确瓶颈和边界后，可替换特定数据平面，而不是重造全部控制面。

**问：可靠 QoS 是否总是更好？**

答：不是。控制消息需要可靠但有 deadline，高频传感器可能更适合 best effort 和丢旧保新；可靠机制如果造成旧消息排队，反而恶化控制延迟。

**问：如何做到跨进程零拷贝？**

答：预分配共享内存 buffer，传递句柄而非 payload，建立 owner/reader 引用协议和回收机制；通知与数据分离，处理崩溃恢复、权限、对齐和版本。最后用端到端数据证明收益。

**问：怎样处理重复、乱序和过期控制指令？**

答：消息携带 ID、序列号、epoch 和 deadline；接收端维护去重和最新版本，拒绝过期或旧代消息；执行操作必须幂等，重连后不能把旧连接的消息当成新消息。

**问：如何证明性能优化有效？**

答：固定环境和数据集，先记录基线，再用 profiling 定位热点，单变量修改后重测。比较 p50/p99、吞吐、CPU、内存、带宽、丢帧和稳定性，确认没有把成本转移到另一个阶段。

## 11.5 一分钟自我介绍模板

“我有 Linux C++ 应用、多线程和网络编程经验，擅长处理并发 I/O、资源生命周期和性能问题。围绕机器人中间件，我系统学习并实现了发布订阅、QoS、发现、序列化、录制回放、弱网重连和多智能体状态同步，并通过基准和故障注入验证端到端延迟、吞吐、丢帧和恢复时间。我关注的不只是 API 调用，而是通信语义、失败处理、数据契约和可观测的性能闭环。”

## 11.6 最终能力清单

达到岗位要求前，应该能够：

- 从数据语义选择 Topic、Service、Action 和 QoS。
- 设计同机 IPC、跨机传输和云边路由。
- 解释序列化、零拷贝、生命周期和版本兼容。
- 设计可恢复的录制、索引、压缩和回放链路。
- 处理发现、租约、状态版本、重复、乱序和网络分区。
- 用 trace、perf 和指标定位尾延迟及资源瓶颈。
- 对断线、重试、限流、降级和故障注入给出具体方案。
- 用测试数据而不是形容词证明“高性能”和“可靠”。
